## 4. Concepts (what / why / how)

### 4.1 `kubectl apply --dry-run=client`

- **What:** Local-side rehearsal; parses YAML, checks schema client-side, prints what *would* happen.
- **Modes:** `client` (local) vs `server` (API server admission/defaulting, no persist).
- **Why:** Catch typos/structural mistakes before touching the cluster.
- **Limit:** Does **not** prove image exists, IAM works, or pods will start.

### 4.2 `kubectl apply` vs `rollout status`

- `apply` = **submit desired state** to API server (declarative).
- Controllers (Deployment → ReplicaSet → Pods) **reconcile asynchronously**.
- `rollout status` = **block until** Deployment reports available replicas ≥ desired.
- **Interview:** *“apply does not guarantee running; it guarantees the request was accepted.”*

### 4.3 Rolling update strategy (your manifest)

| Field | Value | Meaning |
|-------|-------|---------|
| `maxSurge: 1` | +1 extra pod during rollout | capacity to start new before killing old |
| `maxUnavailable: 0` | never intentionally reduce available | zero-downtime (needs room for surge pod) |
| `revisionHistoryLimit: 3` | keep 3 old ReplicaSets | enables `rollout undo` |

**Mid-rollout:** Service endpoints contain **both** old and new pods → mixed `version` in curl is expected.

### 4.4 Probes

| Probe | Path | Role |
|-------|------|------|
| startupProbe | `/health/ready` | grace period during boot (5s × 30 = 150s max) |
| readinessProbe | `/health/ready` | in/out of Service endpoints |
| livenessProbe | `/health/live` | restart container if dead |

Readiness ≠ liveness: unready pod stays alive but receives **no traffic**.

### 4.5 Self-healing & drain

- Delete pod → **ReplicaSet** reconciles count back to `replicas: 2`.
- `cordon` → `SchedulingDisabled` (no new pods; existing keep running).
- `drain` = cordon + **evict** workloads (with `--ignore-daemonsets`, `--delete-emptydir-data` for emptyDir like your `/tmp` volume).
- **Why drain:** safe node upgrade/termination without manual pod moves.
- After uncordon, scheduler may pack pods differently (both pods landed on one node earlier — natural bin-packing, not a bug; topologySpread would fight this).

### 4.6 ECR auth vs node pull (two different trust boundaries)

| Actor | Auth | When |
|-------|------|------|
| Your laptop Docker | `aws ecr get-login-password` → `docker login` | **push** |
| EKS worker nodes | Instance role `AmazonEC2ContainerRegistryPullOnly` | **pull** |

Same account, **separate identities**. ImagePullBackOff troubleshooting: wrong URI? tag missing? node IAM? network path to ECR (NAT/VPC endpoint)?

### 4.7 GitOps with ArgoCD

| Concept | In your lab |
|---------|-------------|
| Source of truth | GitHub `pulse-platform` @ `master`, path `k8s` |
| Desired state | Application CR `syncPolicy` |
| Reconcile | application-controller diffs git ↔ live cluster |
| Sync | apply diffs (ServerSideApply) |
| Health | readiness of Deployment/ReplicaSet/Pods |
| Auto-sync | `automated:` — no human kubectl after push |
| Manual first sync | adopt pre-existing resources cleanly |
| Finalizer | `resources-finalizer.argocd.argoproj.io` → cascade delete on App deletion |

**Imperative vs GitOps tradeoffs:**

| | `kubectl apply` (day 02 morning) | GitOps (ArgoCD) |
|--|--------------------------------|-----------------|
| Speed | Instant | Setup + poll/webhook latency |
| Audit | Terminal history | Git commits + PRs |
| Drift | Invisible until you look | ArgoCD shows OutOfSync |
| Rollback | `rollout undo` or re-apply old | `git revert` + push |
| Access control | cluster RBAC | git RBAC + cluster RBAC |
| Blast radius | anyone with kubeconfig | requires push rights to repo |

### 4.8 Port-forward, ClusterIP, HTTPS — your question

| | Pulse app | ArgoCD UI |
|--|-----------|-----------|
| Protocol | HTTP :8080 | HTTPS :443 (self-signed) |
| Service | ClusterIP (internal only) | ClusterIP (internal only) |
| localhost access | `kubectl port-forward svc/pulse-api 8080:80` | `kubectl port-forward svc/argocd-server 8081:443` |
| Internet-exposed? | **No** | **No** |

- Port-forward tunnels **through the Kubernetes API server** to your loopback — not a cloud LoadBalancer.
- Stop the forward → localhost dies. Nothing is publicly reachable without LoadBalancer/Ingress/NodePort.
- ArgoCD defaults to TLS; your Spring app is plain HTTP. Both are “internal”; only the wire protocol differs.

### 4.9 Automated sync poll interval

- Auto-sync does **not** watch GitHub push events by default — it **polls** (~3 min repo refresh).
- Lab demo needed `argocd.argoproj.io/refresh=hard` to force immediate re-fetch.
- Production options: shorter `timeout`, **GitHub webhook → ArgoCD**, or ApplicationSet with notifications.

## 5. Failure / incident notes (interview gold)

### 5.1 ImagePullBackOff (hypothetical checklist — not hit today)

1. Image exists in ECR? `aws ecr describe-images`
2. URI/tag in deployment correct?
3. Node IAM has ECR **pull** policy?
4. Network path: private subnets → NAT → ECR endpoints (or VPC endpoints)?

### 5.2 Drain blocked: “cannot delete Pods with local storage”

- Your deployment mounts `emptyDir` at `/tmp` (for `readOnlyRootFilesystem`).
- Drain refuses by default → **`--delete-emptydir-data`** (data in emptyDir is ephemeral — safe here).
- **Tradeoff:** flag is dangerous if emptyDir holds real state; your case is tmp only.

### 5.3 Finalizer warning on Application CR

```
Warning: metadata.finalizer: prefer domain-qualified finalizer name
```

- Harmless in lab; ArgoCD’s classic finalizer still works.
- Domain-qualified style (`argoproj.io/...`) avoids name collisions with other controllers.

### 5.4 First ArgoCD sync “already exists”

- Resources created imperatively lack ArgoCD tracking labels.
- **Fix used:** delete Deployment+Service → ArgoCD recreates from git (ownership transfer, ~30s blip).
- Alternative: label existing objects with tracking label, or ServerSideApply adoption.

### 5.5 Auto-sync lag after git push

- Symptom: push done, status still old revision, `Synced/Healthy` (stale).
- Cause: poll interval not elapsed; controller hasn’t re-cloned.
- Fix: hard refresh annotation; production: webhook.

## 6. Interview talking points (day 02)

1. **“Does `kubectl apply` mean the app is running?”**  
   No — it submits desired state; controllers reconcile async; verify with `rollout status` / `get pods`.

2. **“How do you roll back a bad release?”**  
   `kubectl rollout undo` (imperative) or `git revert` + push (GitOps). History via `rollout history` + change-cause annotation.

3. **“Pods on one node — problem?”**  
   Not incorrect, but single-node SPOF for those replicas. TopologySpreadConstraints / anti-affinity spread across AZs/nodes. Your lab naturally re-spread after uncordon.

4. **“Who can pull from ECR — laptop or cluster?”**  
   Both authenticate separately: Docker login (push) vs node instance role (pull).

5. **“Why ArgoCD if kubectl works?”**  
   Audit trail, drift detection, PR-based change control, self-service for devs without cluster creds, consistent multi-env promotion.

6. **“How does ArgoCD reach my private repo?”**  
   Public repo = no creds (your lab). Private = Secret with token/SSH key in argocd namespace.

7. **“Is your app exposed to the internet?”**  
   No — ClusterIP + port-forward only. Real exposure needs LB/Ingress + security groups + TLS.
